# BootLoad引导接入说明

更新：2026-10-20。当前APP已重定位，用户确认旧Bootloader可沿用、升级可用。
Bootload工程由用户维护；本文只描述应用侧约定，不推定Boot端未提供的实现。

## 地址及标志

| 用途 | 地址／值 |
| --- | --- |
| Boot代码预留 | 0x08000000～0x08002FFF |
| 标志专用页 | 0x08003000～0x080037FF，2KiB，第6页（0起算） |
| APP IROM起点／大小 | 0x08003800／0x1A800（106KiB） |
| APP结束地址 | 0x0801DFFF；0x0801E000起为存储保留区 |
| 升级请求／正常标志 | 0／0x55BB |
| 参数页／继电器页 | 0x0801E000／0x0801F000；不得由APP升级入口擦写 |

常量位于`Config/boot_config.h`。原备份页0x0801E800未使用，不应擦写。
Keil Target IROM1与下载范围均采用3800/1A800；当前是自动生成scatter，不用手改生成文件。
已有Boot时下载APP选择Erase Sectors，避免Erase Full Chip。Boot端升级擦除范围也要保留上述存储区。

## 协议

- ASCII：`BootLoad`，大小写固定，严格8字节。
- HEX：`42 6F 6F 74 4C 6F 61 64`。
- 不加0x14地址、CRC、CRLF或其他后缀，不增加确认回复。
- DTO/HIK下UART1、485口1、485口2共用入口。维护窗口内命令可能丢弃，结束后重发。

## 应用侧执行流程

1. `proto_local`精确识别，`app_local`先检查安全布局，暂停模式业务。
2. 等待三路已入队TX完成；任一TX错误或20s超时取消。
3. 暂停RX并清缓存，再次核对布局和TX空闲。
4. `svc_boot`调用`bsp_boot`仅擦标志页，写0并回读。
5. 成功调用系统复位，由旧Boot接管；失败恢复RX，不自动重复擦写/重试/复位。

参数和继电器状态不随升级命令保存。复位会丢失未保存的RAM参数和RAM SN。
启动时`svc_boot_init`在安全布局下维护55BB；已是正常标志不擦页，失败记数后继续运行。
不要在main里再复制旧Flash写入代码。

## 向量、中断及保护条件

main的USER区包含`boot_config.h`、`bsp_system.h`；HAL_Init前设置SCB->VTOR到3800，
执行DSB/ISB后恢复旧Boot关闭的PRIMASK。HAL_Init负责重新初始化SysTick。
Boot跳转前对外设、NVIC、SysTick的清理仍由用户Boot工程正确完成。

只有真实装载区Base和VTOR均为0x08003800、镜像装载末尾大于起点且不超过0x0801E000，
后端才允许标志写入。镜像长度包含初始化RAM数据的Flash副本。
ARMCC5使用`Load$$LR$$LR_IROM1$$Base/Limit`；其他工具链须显式适配，不能取消保护。

当前编译map为起点0x08003800、装载末尾0x0800CF40。若以后改回0x08000000直连构建，
启动不写标志，BootLoad会被拒绝，避免擦掉应用代码。

## 验证和诊断

`svc_boot_get_status`可读startup_marks、requests、failures、layout_rejects；
`app_local_get_status`反映公共维护事务状态。
软件覆盖两模式三口、排空/互斥/失败/布局拒绝等20场景，以及只擦标志页等13个实际BSP模拟场景。
用户已确认旧引导升级通过；未据此声称所有端口/模式组合和升级前后存储保持都已实测。
